# Prioritization

## Core Concepts

- Not all requirements are equal — value, risk, and dependencies determine order
- Prioritization is a forcing function: it makes trade-offs explicit, not hidden
- Multiple frameworks exist (MoSCoW, WSJF, RICE); pick one that fits your decision context
- Priority changes as context changes — re-evaluate at each planning boundary
- Cost of delay is the most reliable signal: what do we lose by not doing this now?

## Key Practices

- Score requirements on value AND effort — high value alone doesn't mean "do first"
- Use cost of delay: revenue impact, regulatory deadlines, blocking dependencies
- Identify dependencies between requirements — some items unlock others
- Separate "must have for launch" from "must have eventually" using hard constraints
- Present trade-offs to stakeholders as choices, not recommendations — let them own priority

## Common Mistakes

- Treating all requirements as P1: when everything is urgent, nothing is prioritized
- Prioritizing by who shouts loudest instead of by measurable impact
- Never re-prioritizing: the backlog becomes a graveyard of outdated wishes

## When to Apply

- Backlog has more items than team capacity for the next 3 sprints
- Stakeholders disagree on what to build next
- Release scope needs to be cut — deciding what stays and what goes
- Planning a new quarter or roadmap cycle
